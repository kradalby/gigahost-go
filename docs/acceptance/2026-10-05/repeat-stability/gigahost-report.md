Fresh-install and API stability findings from three Terraform acceptance rounds through gigahost-go, 2026-10-05. Inputs: performance, 2c-4gb-40gb, sfj, amd64; OS IDs 101/108/102/116/117/95/105; account SSH key 2954. Each installation is fresh, with its own VM and Terraform state. Acceptance requires API running state plus root SSH executing `hostname`.

**Cleanup update, 2026-10-09:** the user requested cancellation of all remaining running servers. All 14 previously retained debugging VMs were cancelled and the active server list was verified empty; [cleanup evidence](cleanup-2026-10-09.json) records the operation. References below to retained VMs describe the investigation on 2026-10-05. Those guests are no longer available for inspection; recorded inputs, API exchanges and test evidence remain available.

1. **Root SSH fails for AlmaLinux 10, RockyLinux 9 and Fedora 43 Server.** Each image rejected both its requested key and captured password in all three trials. Debian 12/13 and Ubuntu 24.04/26.04 passed both methods in all three trials. The saved installer commands contain the same public key used successfully on the other images. All seven third-round password trials saved the exact state credential separately and matched it against the API installer credential; [credential-validation.json](credential-validation.json) records those checks and public-key comparisons. Please confirm the intended root SSH policy for these images and inspect credential installation on retained VMs 18866, 18867, 18870, 18871, 18878 and 18879. We need actual authorized-key contents/permissions/SELinux labels, effective sshd configuration and authentication logs; installer-context or root-policy causes remain hypotheses. Further evidence: all 42 deploy requests differ only in `os_id` and `hostname`. sshd answered from the first or second attempt and then rejected 11–18 logins in a row, and a late check 70–93 minutes after install still failed, so this is not boot timing. On key VMs sshd still offered `password`, although the post-install script sets `PasswordAuthentication no`. The RHEL-family post-install script writes to bare `/root/...` and `/etc/ssh/...`, while the Debian/Ubuntu scripts write to `/target/...`. Is the RHEL script running outside the installed system, or overridden by an `sshd_config.d` drop-in? RHEL 9+ and Fedora also block root password SSH unless kickstart sets `rootpw --allow-ssh`.

2. **Allocation and installation delay varies substantially.** Orders 36004/36005/36006 took 950/960/980 seconds to expose a VM ID and 2360/2310/2370 seconds to become ready. VMs were 18868/18869/18870. The following installer waiting phase remained around 17 minutes without stalled/failed flags. Other orders allocated sooner, and round-two readiness was 160–400 seconds. Please explain queue/installer waiting semantics, expected startup bounds and when stalled should become true. We used a test-only 45-minute allowance to observe completion; normal provider timeout remains 15 minutes.

3. **Undocumented required fields (withdrawn as defects; resolved on our side).** `POST /servers/{id}/ipv4` with `{"ip_type":"l3"}` returned `Invalid data received.`, and rDNS `PUT /servers/{id}/reverse` with `{"ip_id":"7797","dns":"acc-test1.example.com"}` returned a bare 400. The [API documentation](https://gigahost.no/en/api-dokumentasjon) now requires `num_ips` for the IPv4 order and `v4v6` for rDNS; earlier versions did not list them. Our client now sends both. Requests: return a validation message naming a missing field; confirm whether `num_ips` other than 1 has meaning; confirm that numeric strings are accepted for numeric body fields.

4. **Snapshot completion/visibility needs investigation.** Snapshot 7055 on VM 18881 did not reach completed within ten minutes. Snapshot 7056 on VM 18884 appeared after create and was later absent; our provider then dropped it from state without an error (a provider defect, now fixed), and DELETE returned 400 `Unable to delete. Snapshot not found.` rather than 404; a later read-only check still returned an empty snapshot list. Snapshot 7057 on VM 18902 completed in about 50 seconds. In a focused repeat, snapshot 7061 on VM 18928 remained pending for about 60 seconds and then disappeared from the list before any DELETE request. It stayed absent through the ten-minute completion deadline, and the later cleanup DELETE returned Snapshot not found; its full API history is recorded. A read-only server check at 16:15 UTC found the VM still running, not installing, with no active snapshot operation. The final focused trial repeated the pending-to-absent transition with snapshot 7062 on VM 18931 at about 60 seconds, also before any DELETE. Timing correlates: 7061 and 7062 were requested 1–2 seconds after the server first reported install finished and vanished at about 60 seconds; 7057 and 7059 were requested about 48 seconds after and completed in about 50 seconds. The guest was likely still on first boot. The sample is small. Please explain why these snapshot jobs disappear without a terminal failure state or error reason, whether a snapshot during first boot is expected to fail, and why the create was acknowledged with 200. Successful asynchronous deletion acknowledgements followed by deleting state are tracked separately; our earlier immediate deletion assertion was corrected.

5. **Reinstall holds the request past 60 seconds after starting.** The default reinstall path sent an empty hostname, which the documentation allows (the server's primary IP is used instead), and timed out awaiting headers at the client’s 60-second limit like the explicit-hostname trials. For VM 18930, `install_details.date_started` matches the second the request was sent, so the install starts immediately while the response is held. Explicit-hostname trial outcomes and actual request bodies are listed below. VM 18930 changed from os_id 108 to 101 and reported installing immediately after its 60-second response timeout, so the request did take effect despite the caller receiving an error. The documentation says the call returns once the install has started. Please clarify the acknowledgement latency, whether it responds at all, and how callers should obtain the install result reliably. Our provider now reads the server back after a timeout and continues only when the requested OS is installing. Also: `srv_hostname` is empty on every live server while the deploy hostname is held in `srv_name`; which field holds the guest hostname, and which one does the reinstall `hostname` update?
